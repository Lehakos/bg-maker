# BG Maker: Playable Prototype Vision

Этот документ фиксирует рабочее понимание проекта для разработки. Это не
маркетинговое описание, а продуктово-техническая опора: какую систему мы
строим, какие сущности нужны, что входит в первый играбельный MVP и куда
можно развивать проект дальше.

## Core Idea

BG Maker - конструктор играбельных прототипов настольных игр.

Цель не в том, чтобы просто нарисовать материалы для печати или собрать набор
ассетов. Пользователь должен иметь возможность создать игру, описать ее
компоненты, разложить их на виртуальном столе и сразу сыграть в прототип прямо
в браузере.

Главный цикл продукта:

```text
Создать игру
-> описать компоненты
-> настроить зоны и стартовую раскладку
-> запустить партию
-> сыграть / протестировать
-> сохранить наблюдения
-> изменить прототип
-> повторить
```

Короткая формула:

```text
Game Definition + Initial Setup + Action System = Playable Session
```

## Product Shape

BG Maker должен быть не просто редактором ассетов и не просто виртуальным
столом. Это среда, где прототип настольной игры существует как набор связанных
сущностей:

- компоненты игры;
- игровые зоны;
- стартовая раскладка;
- допустимые действия;
- состояние партии;
- история действий;
- заметки плейтеста;
- версии прототипа.

На ранних этапах важно поддержать ручной и полуавтоматический режим игры.
Полноценный движок правил можно развивать постепенно, но MVP должен позволять
сыграть даже без формальной автоматизации всех правил.

## Core Loop

Пользовательский сценарий, который должен быть возможен как можно раньше:

1. Создать проект игры.
2. Добавить базовые компоненты: карты, колоды, жетоны, счетчики, зоны.
3. Настроить стартовую раскладку.
4. Запустить игровую сессию.
5. Двигать компоненты по столу и между зонами.
6. Перемешивать колоды, брать карты, открывать и скрывать информацию.
7. Менять счетчики и состояния компонентов.
8. Сохранить состояние партии и заметки.
9. Вернуться в редактор, поправить прототип и запустить новую сессию.

## Main Entities

### Game Project

Контейнер всей игры.

Должен хранить:

- название;
- описание и рабочие заметки;
- статус: черновик, тестируется, готово;
- версии;
- список компонентов;
- игровые зоны;
- стартовые раскладки;
- плейтест-сессии.

### Component Model

Компонент - любая физическая или логическая сущность игры.

Возможные типы:

- card;
- deck;
- token;
- tile;
- board;
- player board;
- counter;
- die;
- marker;
- bag;
- zone.

Компонент должен быть не только визуальным, но и интерактивным.

Пример свойств карты:

- лицевая сторона;
- рубашка;
- поля данных;
- теги;
- владелец;
- состояние: hidden, revealed, tapped, exhausted, selected;
- допустимые действия.

### Table And Layout

Стол описывает игровое пространство и расположение объектов.

Возможные элементы:

- общая область стола;
- зоны игроков;
- приватные зоны;
- колоды;
- сбросы;
- рынки;
- треки;
- ячейки;
- свободные области.

Архитектурно стоит держать в голове гибридную модель: свободное перемещение
объектов, как на физическом столе, плюс структурные зоны, которые помогают
автоматизировать типовые действия.

### Actions

Действия - центральная часть playable-прототипа. На первом этапе это может быть
универсальный набор tabletop-действий, а не полноценный rules engine.

Базовые действия:

- move component;
- draw card;
- shuffle deck;
- reveal / hide;
- flip;
- rotate;
- tap / exhaust;
- discard;
- clone / spawn;
- increment counter;
- roll die;
- choose option;
- transfer resource.

Важно, чтобы действия меняли состояние партии и попадали в action log. Это
позволит сохранять партии, анализировать плейтесты и позднее добавлять откаты,
повторы или автоматическую проверку правил.

### Play Session

Play Session - конкретная запущенная партия конкретной версии игры.

Должна хранить:

- gameId;
- versionId;
- players;
- текущее состояние стола;
- состояние компонентов;
- action log;
- заметки;
- время сессии;
- статус сессии;
- snapshots.

### Rules And Automation

Автоматизация правил - отдельный слой поверх базового игрового стола.

Возможная эволюция:

1. Ручной режим: игроки сами делают все действия.
2. Полуавтоматические действия: добор, сброс, перемешивание, счетчики.
3. Простые триггеры: после действия выполнить эффект.
4. Структура хода: фазы, активный игрок, ограничения.
5. Проверка правил: допустимые действия, условия победы, валидация ходов.

MVP не должен зависеть от полноценного rules engine. Сначала нужен надежный
игровой стол и универсальная модель состояния.

## MVP Scope

Первый полезный MVP: playable tabletop builder.

Минимально ценные возможности:

- создать проект игры;
- создать карты;
- создать колоды;
- создать игровые зоны;
- настроить стартовую раскладку;
- запустить сессию;
- двигать карты между зонами;
- перемешивать колоды;
- брать карты;
- открывать и скрывать карты;
- вести счетчики;
- сохранять состояние партии.

Этого достаточно, чтобы пользователь мог создать простую карточную или
настольную игру и реально сыграть в нее в браузере.

## Later Features

После первого playable-MVP можно развивать следующие направления:

- мультиплеерные комнаты по ссылке;
- player seats и приватная информация;
- observer mode;
- права на действия;
- версии прототипов;
- changelog между версиями;
- заметки по компонентам и сессиям;
- quick edit из плейтеста;
- экспорт print-and-play материалов;
- экспорт изображений компонентов;
- импорт данных из таблиц;
- шаблоны жанров и стартовых наборов;
- scripted actions;
- симуляции и инструменты балансировки.

## Design Principles

- Играбельность важнее декоративности.
- Ручной режим должен работать раньше полной автоматизации.
- Любое действие должно быть отражено в состоянии партии.
- Игровые зоны должны помогать прототипированию, но не мешать свободному
  эксперименту.
- Компоненты должны быть data-driven, чтобы пользователь мог быстро менять
  параметры и массово создавать варианты.
- Плейтест должен быть частью рабочего процесса, а не отдельной внешней
  активностью.
- Система должна поддерживать быстрый цикл: изменить -> сыграть -> заметить
  проблему -> изменить снова.

## Open Questions

- MVP должен начинаться с карточных игр или сразу поддерживать более общий стол?
- Насколько свободным должен быть layout: canvas-like tabletop или строгие зоны?
- Где проходит граница между component editor и rules editor?
- Нужно ли сразу проектировать multiplayer-first архитектуру?
- Как хранить версии: snapshot всей игры или миграции изменений?
- Какие действия должны быть универсальными, а какие зависят от типа игры?
- Нужно ли в MVP поддерживать экспорт для печати или сначала только playable
  browser-сессии?
