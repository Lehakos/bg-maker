# BG Maker: Tabletop Engine Vision

Этот документ описывает новое видение BG Maker как игрового движка и редактора
для настольных игр. Он намеренно не привязан к текущей реализации и не описывает
маппинг существующих сущностей. Его задача - зафиксировать продуктовую и
архитектурную цель, к которой мы хотим двигаться.

## Короткая Формула

BG Maker - это узкоспециализированный tabletop engine для создания, раскладки и
ручного тестирования настольных игр.

Публичная модель должна быть простой:

```text
Project
  Table Setups
  Object Library
  Playtests
```

Главная идея:

```text
A Table Setup is built from Objects.
Any Object can contain other Objects.
Any Object can be saved, reused, and specialized.
A Playtest starts from a Table Setup.
```

Первая версия не должна автоматизировать правила игры. Она должна дать автору
настолки удобную среду, где можно:

- создать проект игры;
- создать игровые объекты;
- собрать стартовую раскладку стола;
- вручную протестировать прототип;
- быстро вернуться к редактированию после плейтеста.

## Принципы

### Tabletop-Native, А Не Универсальный Game Engine

BG Maker не должен конкурировать с Unity, Godot или Unreal как универсальный
движок. Его сила должна быть в том, что он понимает предметную область
настольных игр.

Пользователь должен работать с понятными tabletop-объектами:

- cards;
- decks;
- tiles;
- pieces;
- dice;
- boards;
- tables;
- zones;
- hands;
- bags;
- counters;
- score tracks;
- player areas.

Под капотом у редактора может быть дерево, ссылки, экземпляры и переопределения,
но пользовательская модель должна оставаться проще: table setups и objects.

### Меньше Сущностей, Больше Смысла

В публичной модели не нужны отдельные `Scene`, `Node`, `Prefab`, `Component`,
`Resource` и `Instance`.

Вместо этого:

- `Table Setup` - корневая игровая раскладка;
- `Object` - любой элемент внутри раскладки или библиотеки;
- `Object Library` - место, где хранятся переиспользуемые объекты;
- `Playtest` - запущенное состояние table setup.

Слова вроде prefab, node или instance могут существовать внутри кода, но не
должны быть основными терминами интерфейса.

### Ограниченность Как Преимущество

Редактор должен быть ближе к Godot по структуре, но ближе к RPG Maker и
Construct по ощущению: меньше бесконечной свободы, больше готовых решений.

Хороший путь для автора должен быть очевидным. Пользователь открывает проект и
сразу видит рабочую среду, а не пустую IDE, которую нужно сначала настроить.

### Ручной Плейтест Сначала

Правила и автоматизация важны, но они не должны быть фундаментом первой версии.

Первая версия должна позволять сыграть в прототип вручную:

- двигать объекты;
- переворачивать карты;
- тасовать колоды;
- брать карты;
- бросать кубы;
- менять счетчики;
- складывать и раскладывать объекты;
- скрывать и раскрывать информацию;
- фиксировать действия в истории.

Если ручной режим будет надежным, поверх него позже можно добавить правила,
скрипты, фазы хода, ограничения и автоматические эффекты.

### Данные Важнее Экрана

Интерфейс редактора может меняться, но модель проекта должна быть устойчивой.

Важные вещи должны существовать как данные:

- структура проекта;
- table setups;
- object library;
- вложенность объектов;
- свойства объектов;
- связи между объектами;
- начальное состояние;
- состояние плейтеста;
- история действий.

Это позволит сохранять, версионировать, повторять и анализировать прототипы.

## Основные Сущности

### Project

Проект - корневой контейнер игры.

Он содержит:

- метаданные игры;
- table setups;
- object library;
- плейтесты;
- настройки редактора;
- заметки автора.

Проект должен открываться как рабочая среда, а не как набор отдельных страниц.

### Table Setup

Table Setup - корневая игровая раскладка.

Это главный редактируемый контекст, который можно открыть в редакторе и
запустить в playtest. По смыслу это стартовое состояние партии или отдельный
вариант стартовой раскладки.

Примеры:

- `Main Table`
- `2 Player Setup`
- `Solo Setup`
- `Tutorial Setup`
- `Final Round Test`

Table Setup состоит из объектов. Например:

```text
Table Setup: 2 Player Game
  Object: Table
  Object: Player Area
  Object: Player Area
  Object: Main Board
  Object: Market Row
  Object: Resource Deck
  Object: Token Supply
```

В проекте может быть несколько table setups для разных сценариев тестирования.

### Object

Object - базовая единица BG Maker.

Object может быть чем угодно:

- одиночной картой;
- колодой;
- жетоном;
- тайлом;
- кубиком;
- счетчиком;
- зоной;
- игровым столом;
- доской;
- областью игрока;
- группой объектов;
- текстом;
- изображением;
- сложным переиспользуемым фрагментом раскладки.

Object может содержать другие objects.

Например:

```text
Object: Player Area
  Object: Hand
  Object: Draw Deck Slot
  Object: Discard Slot
  Object: Score Counter
```

Или:

```text
Object: Resource Card
  Object: Card Face
  Object: Resource Icon
  Object: Resource Name
  Object: Resource Value
```

### Built-In Objects

Движок предоставляет встроенные типы объектов, из которых пользователь может
собирать свои собственные объекты.

Базовый набор:

- `Table`
- `Board`
- `Zone`
- `Card`
- `Deck`
- `Hand`
- `Tile`
- `Piece`
- `Die`
- `Counter`
- `ScoreTrack`
- `Bag`
- `PlayerArea`
- `Text`
- `Image`
- `Group`

Каждый встроенный тип должен иметь понятные свойства и ожидаемые действия.

Например:

- `Card` умеет переворачиваться;
- `Deck` умеет тасоваться и отдавать карту;
- `Die` умеет бросаться;
- `Counter` умеет увеличиваться и уменьшаться;
- `Zone` умеет принимать другие объекты;
- `Group` умеет объединять несколько объектов в один редактируемый фрагмент.

### Custom Objects

Пользователь может создавать свои объекты поверх встроенных.

Например, в движке есть встроенный объект `Card`. Пользователь может создать
свой объект `ResourceCard`, который будет служить общей основой для всех карт
ресурсов.

Потом на основе `ResourceCard` можно создать конкретные карты:

```text
Built-In Object: Card
  Custom Object: ResourceCard
    Custom Object: WoodCard
    Custom Object: GoldCard
    Custom Object: StoneCard
```

`ResourceCard` может определить общую структуру:

- размер карты;
- рубашку;
- расположение названия;
- место для иконки ресурса;
- место для значения;
- общий стиль.

`WoodCard` и `GoldCard` переиспользуют эту структуру, но меняют конкретные
данные:

- название;
- иконку;
- цвет;
- значение;
- описание.

Так пользователь не обязан каждый раз собирать карту с нуля. Он может создать
объект-основу и делать от него более конкретные объекты.

### Object Library

Object Library - библиотека переиспользуемых объектов проекта.

В ней могут лежать:

- карты;
- колоды;
- жетоны;
- зоны;
- области игроков;
- треки очков;
- рынки карт;
- заготовки столов;
- визуальные элементы;
- любые сложные объекты, которые автор хочет использовать повторно.

В UI библиотеку можно фильтровать по категориям:

- all;
- cards;
- decks;
- tokens;
- tiles;
- dice;
- boards;
- zones;
- layouts;
- text and images.

Категории нужны для навигации, но не должны становиться отдельными
фундаментальными сущностями.

### Object Specialization

Object может быть создан на основе другого object.

Это должно ощущаться не как техническое наследование, а как понятная автору
настолок операция:

- create object from;
- save as reusable object;
- duplicate object;
- edit source object;
- override property;
- detach from source.

Пример:

```text
ResourceCard
  defines size, layout, icon slot, title slot, value slot

WoodCard based on ResourceCard
  overrides title = "Wood"
  overrides icon = wood icon
  overrides color = green

GoldCard based on ResourceCard
  overrides title = "Gold"
  overrides icon = coin icon
  overrides color = yellow
```

Если автор меняет общий layout в `ResourceCard`, конкретные ресурсные карты
должны получить это изменение, пока они не переопределили соответствующее
свойство локально.

Это дает силу prefab-подхода, но без необходимости делать `Prefab` отдельной
публичной сущностью.

### Placed Objects

Когда объект из библиотеки добавляется в table setup, он становится размещенным
объектом.

Пользователю не нужно знать отдельный термин `instance`, но поведение должно
быть понятным:

- объект можно вставить в table setup;
- вставленный объект можно двигать, поворачивать и настраивать;
- локальные изменения могут быть переопределениями;
- объект можно отвязать от исходного reusable object;
- объект можно сохранить обратно как новый reusable object.

Пример:

```text
Object Library
  ResourceCard
  WoodCard
  GoldCard
  PlayerArea

Table Setup: Main Table
  PlayerArea x2
  Deck containing WoodCard and GoldCard
  Market Zone
  Token Supply
```

## Редактор

Редактор должен быть главным экраном проекта.

Базовая структура:

```text
┌────────────────────────────────────────────────────────────┐
│ Toolbar: Select Move Rotate Playtest Undo Redo Save ...    │
├───────────────┬────────────────────────────┬───────────────┤
│ Object Tree   │                            │ Inspector     │
│               │        Viewport            │               │
│ Setup Objects │                            │ Properties    │
├───────────────┴────────────────────────────┴───────────────┤
│ Object Library / Commands / Problems / Playtest Log         │
└────────────────────────────────────────────────────────────┘
```

Панели должны быть настраиваемыми: пользователь может менять их размер,
скрывать и возвращать.

### Object Tree

Object Tree показывает иерархию объектов в выбранном table setup или в
редактируемом reusable object.

Ожидаемые возможности:

- выбрать объект;
- переименовать объект;
- создать дочерний объект;
- удалить объект;
- изменить порядок;
- сгруппировать объекты;
- раскрывать и сворачивать ветки.

### Object Library Panel

Object Library Panel показывает переиспользуемые объекты проекта.

Из библиотеки объект можно:

- открыть для редактирования;
- перетащить во viewport;
- вставить в object tree;
- дублировать;
- использовать как основу для нового объекта.

### Viewport

Viewport - центральная рабочая область.

В нем пользователь видит выбранный table setup или редактируемый object,
перемещает компоненты, редактирует размеры, повороты, зоны и взаимное
расположение.

Viewport должен поддерживать:

- selection;
- pan;
- zoom;
- drag and drop;
- snapping;
- resize handles;
- rotate handles;
- grid;
- visual previews;
- edit/playtest mode.

### Inspector

Inspector показывает свойства выбранного объекта.

Он должен быть контекстным: свойства карты отличаются от свойств зоны, колоды,
кубика или счетчика.

Inspector не должен содержать сложную бизнес-логику. Его задача - отображать и
редактировать свойства выбранного object через команды редактора.

### Toolbar

Toolbar должен содержать основные инструменты:

- select;
- move;
- rotate;
- create object;
- duplicate;
- delete;
- save as reusable object;
- undo;
- redo;
- save;
- playtest;
- stop playtest;
- zoom controls.

Кнопки должны быть компактными и узнаваемыми, с иконками и tooltips.

## Commands

Command - действие, которое меняет table setup, object или состояние плейтеста.

Редакторские команды:

- create object;
- delete object;
- move object;
- rename object;
- change property;
- duplicate object;
- group objects;
- save object to library;
- create object from source;
- detach object from source.

Плейтест-команды:

- move object;
- flip card;
- shuffle deck;
- draw card;
- roll die;
- set counter;
- stack objects;
- reveal object;
- hide object.

Командная модель нужна для undo/redo, истории действий, сохранения сессий и
будущего мультиплеера.

## Playtest

Playtest - конкретный запуск table setup в игровом режиме.

Он должен хранить:

- исходный table setup или snapshot;
- текущее состояние размещенных объектов;
- историю действий;
- заметки;
- время сессии;
- статус.

Плейтест должен ощущаться как продолжение редактора: автор переключается в
режим игры, тестирует идею, возвращается назад и правит прототип.

## V1 Scope

Первая версия нового направления должна быть узкой, но цельной.

Входит:

- создание и открытие проекта;
- единый редактор проекта;
- table setups;
- object library;
- object tree;
- viewport;
- inspector;
- базовые встроенные objects;
- создание custom objects поверх встроенных;
- создание объектов на основе других объектов;
- стартовая раскладка;
- ручной playtest mode;
- история действий;
- undo/redo для редактора;
- сохранение проекта.

Не входит:

- полноценный rules engine;
- визуальное программирование;
- скрипты;
- AI players;
- автоматическая проверка победы;
- сложная физика;
- 3D-редактор;
- публичный marketplace;
- продвинутый multiplayer.

## Что Заимствовать У Существующих Движков

### У Godot

- редактируемые фрагменты, которые можно вкладывать друг в друга;
- дерево объектов;
- inspector;
- переиспользуемые объекты;
- режим редактирования и запуска;
- простая, строгая структура проекта.

### У Unity

- object instances;
- overrides;
- asset/object browser;
- transform tools;
- command history;
- play mode как отдельное состояние.

### У RPG Maker И Construct

- ограниченный, понятный набор возможностей;
- готовые типы объектов;
- быстрый старт;
- меньше технического шума;
- шаблоны типовых сценариев.

## Что Делать Иначе

BG Maker должен быть tabletop-native.

В универсальных движках пользователь сам собирает карточную игру из примитивов.
В BG Maker карта, колода, рука, зона и счетчик должны быть базовыми объектами.

Правила должны добавляться поверх ручной модели, а не заменять ее. Даже когда в
будущем появится автоматизация, пользователь должен иметь возможность вручную
поправить состояние стола во время теста.

## Будущие Слои

После стабильной первой версии можно развивать следующие слои:

- versioning;
- multiplayer;
- player seats and hidden information;
- simple scripted actions;
- turn structure;
- phases;
- visual rule blocks;
- validation;
- win/loss conditions;
- playtest analytics;
- print-and-play export;
- object image export;
- templates for common game genres.

Эти слои не должны ломать базовую модель. Они должны расширять уже существующие
table setups, objects, commands и playtests.

## Главный Критерий Успеха

Автор настольной игры должен открыть BG Maker, создать несколько objects,
разложить их на столе и начать тестировать прототип без написания правил.

Если после первой версии пользователь может быстро проверить идею игры руками,
значит направление выбрано правильно.
